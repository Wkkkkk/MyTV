MyTV Architecture

Personal IPTV web app — Rust/Axum routes, stream proxy, yt-dlp resolver, SQLite. Generated 2026-06-16.

Request Flow

  • • Clients hit a reverse proxy (TLS) → Axum on :3000
  • • /channel/:id/tune & /next return JSON 200/503
  • • /stream-proxy fetches + rewrites HLS/DASH manifests
  • • guide & admin use HTMX partials; auth on /admin·/api

Core Modules

  • • proxy.rs — redirect-follow, SSRF guard, manifest rewrite
  • • media/resolver — yt-dlp behind a 2-permit semaphore
  • • broadcast.rs — ended live broadcast → vod_loop conversion
  • • health task — 15-min loop, auto-disable/re-enable sources

Data & Deploy

  • • SQLite via SQLx compile-time checked queries
  • • migrations 001–007; model/ wraps all DB access
  • • live_cache: in-memory yt-dlp status, 60s TTL
  • • Fly.io single 256 MB VM; /health check

EPG / VOD Timing — loop position math

How wall-clock time maps to a playlist position. Every request recomputes it from loop_anchor + Utc::now() — nothing is stored.

Live → Ended → VOD lifecycle

A live broadcast resolves through a closed LiveResolution enum; when it ends, a detached task converts the channel into a looping VOD recording.

VOD On-Demand channels — viewer-driven playback

A third channel type (migration 007). Unlike vod_loop, there is no clock and no loop_anchor — the viewer explicitly picks items, and playback always starts at offset 0.
