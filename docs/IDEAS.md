40. **yt-dlp worker pool: queue metrics + priority** — replace the 2-permit semaphore gate (`resolver::run_under_cap`) with a fixed worker pool fed by a bounded channel: callers send a job + `oneshot` reply channel, N worker tasks consume. A semaphore can't report queue depth or reorder its wait queue; a channel-fed pool gives (1) queue-depth/wait-time metrics for `/admin/metrics`, (2) priority — interactive tune/resolve requests jump ahead of background live-status probes (two channels or a priority-aware dispatcher), (3) load-shedding via `try_send`/bounded wait, preserving today's Busy semantics. Keep the global cap at 2 (memory bound: ~73 MB per yt-dlp process on the 256 MB VM).

43. **Bilibili VOD playback** — tune Bilibili videos (`bilibili.com/video/BV…`) as VOD sources. Playback is currently unsupported — see the documented limitation in `docs/superpowers/plans/2026-06-09-bilibili-support.md` (the earlier Bilibili work only covered the youtube-watcher skill's transcripts). Three known blockers: (1) `resolver::needs_resolution` only routes `youtube.com`/`youtu.be`/`twitch.tv` through yt-dlp, so Bilibili URLs are never resolved; (2) Bilibili requires `--cookies-from-browser chrome` to bypass HTTP 412; (3) Bilibili delivers `.m4s` muxed streams (separate video+audio over direct HTTPS), not HLS `.m3u8`/DASH `.mpd`, which the `<video>`/hls.js/dash.js player can't play directly. Needs: add `bilibili.com` to the resolver host list, thread cookies through the yt-dlp call, and handle the separate video+audio streams (see test plan `docs/superpowers/specs/2026-06-09-bilibili-support-test-plan-design.md`).

    **Spike (2026-06-14, yt-dlp 2026.03.17 + Chrome cookies):** the "open unknown" is resolved — Bilibili is **DASH-only with no combined progressive format**. Tested `BV1ceVh6tEe9` and `BV1GpEs6gEAA`: every format is `audio only` or `video only`; a combined-format selector (`b[acodec!=none][vcodec!=none]`) fails with "Requested format is not available". Default best resolves to **two** signed `.m4s` URLs (one video, one audio) on `*.akamaized.net`, each with an `upsig`/`deadline` that **expires in hours** (so resolution must happen at tune/add time, not be stored). So there is no "simplest direct-MP4" path. Two viable approaches:
    - **A. Synthesized DASH** — build an `.mpd` referencing both `.m4s`, play via the existing dash.js path; segments proxied with `Referer: bilibili.com` injection. True streaming, no storage (fits the 256 MB VM), but most code + MPD/byte-range risk + a new proxy header path.
    - **B. Download+mux at add-time** — yt-dlp+ffmpeg mux (stream copy, no re-encode) the two streams into one MP4, persist it, serve as an ordinary VOD (reuses the `broadcast.rs` convert-and-persist pattern). Most reliable, zero browser Referer/CORS issues, but needs ffmpeg + storage and brushes the project's "no transcoding" principle.

    **Key constraint:** running on the public Fly instance is the cost driver — it forces a `cookies.txt` secret (the `--cookies-from-browser` flag needs a real browser, absent on the headless VM) plus, for B, a Fly volume. Local-only B is by far the simplest path if the prod requirement is dropped.

    **Decision (2026-06-14):** shelved after a brainstorming session — neither A's complexity nor B's storage/ffmpeg/"no-transcoding" cost is worth paying right now. Revisit when Bilibili playback is worth the cost; the choice is essentially "local-only B (simple)" vs "prod B (storage+ffmpeg)" vs "A (streaming, most code)".

50. **Collapse the model-layer CRUD triplication** *(architecture deepening, 2026-06-16; Speculative)* — `source.rs` (724), `playlist_item.rs` (669), and `channel.rs` (588) repeat the same skeleton (`Row`/`NewRow`/`UpdateRow`/`Input` + `create`/`get`/`list`/`delete`/`set_active`/`update`) — ~2,000 lines of mostly SQL-binding boilerplate. **Low-risk first step DONE (2026-06-16):** the string-parameterized `model::update_health_sql` (which `format!`'d a table name into SQL — the *only* dynamic-table-name query in the codebase — shared across two tables) is retired; `source::update_health` and `playlist_item::update_health` now each inline a literal-table-name query, killing the silent field-skew hazard. **Note on the broader collapse:** the original framing assumed SQLx compile-time-checked `query_as!`, but the codebase does *not* use the checked macros anywhere — all query sites use the runtime `sqlx::query(...)`/`query_as::<_, T>(...)` function forms with literal SQL (no `.sqlx` offline cache; CI sets no build-time `DATABASE_URL`). So a generic `CrudModel<T>` trait would not be giving up compile-time checking that exists today; the real constraint is keeping each query a self-contained *literal* string (the convention the first step restored), which a runtime-generic trait building `format!` strings would violate. A per-table *macro* expanding literal queries remains the most faithful path if the collapse is pursued. (Candidate #5 from the round — unify HLS+MPD manifest rewriting — was *not* recorded; it risked a forced abstraction and needs a spike first.)

51. **Redesign the player overlay — VOD-on-demand fit + mobile/touch** — the player overlay (`#player-toolbar` in `templates/guide.html`, plus the player/keyboard logic in `templates/base.html` ~L667–820) was designed around keyboard-driven live/`vod_loop` viewing and fits poorly elsewhere. Two problems: **(1) VOD-on-demand compatibility** — the overlay's model is up/down *channel* navigation (`↑`/`↓`), and seek (`←`/`→`) is gated to `vod_loop` only (`currentChannel.channel_type !== 'vod_loop'` returns early), so on-demand channels — which are really *playlist* navigation (prev/next item via the `☰` panel) — get a toolbar built for a different interaction model; the controls and the playlist panel don't form one coherent scheme. **(2) Mobile / no keyboard** — every primary interaction is a key press (Space play/pause, `↑`/`↓` channel, `←`/`→` seek, `F` fullscreen), and the only on-screen affordances are the small toolbar glyphs (`✕ ↑ ↓ ☰ ?`); there's no touch-friendly seek, no swipe/tap navigation, and the help overlay only lists keyboard shortcuts — useless on a phone. Redesign the overlay around touch-first, channel-type-aware controls (distinct affordances for live vs. vod_loop vs. vod_on_demand) with keyboard shortcuts as an enhancement rather than the primary path. Needs a brainstorming/design pass before implementation.

52. **Per-item rows for VOD-on-demand channels in the EPG** — in the guide, a `vod_loop` channel renders one clickable `.program` block *per item* (laid out by schedule time via `epg::vod_schedule`), but a `vod_on_demand` channel renders a *single* `{name} — On demand` block spanning the whole window (`epg::on_demand_entry`, `src/routes/guide/data.rs:121`); clicking only tunes the channel, and individual items are reachable solely through the player's `☰` playlist panel. Better: render each on-demand item as its own clickable block showing its title, so a viewer can click straight to a specific item like they can with vod_loop (the `tune`-a-specific-item path already exists via the player's `item` handler). Because on-demand has *no time schedule*, the items can't be positioned proportionally on the timeline — instead **lay them out as evenly-aligned blocks and cap the title width** (truncate/ellipsis) so long titles don't blow out a block or break the alignment. For consistency, **apply the same title width cap to vod_loop items** too, so all VOD item titles truncate uniformly. Touches `src/epg.rs` (replace the single `on_demand_entry` with per-item entries), `src/routes/guide/data.rs`, `templates/partials/epg_content.html`, and the `.program`/`.program-title` CSS in `templates/base.html`.

53. **Revisit error handling for VOD-on-demand channels (unavailable items)** — when a self-hosted MP4 item is deleted from R2 (or otherwise goes unreachable), two things fail quietly today: **(1) Reporting** — the player's `item` handler returns a bare `503 SERVICE_UNAVAILABLE` with no detail (`src/routes/player.rs:84`, the `resolver::resolve_url` error arm), so the viewer just sees a generic "Channel unavailable"; we should report *which item* is gone and why, both in the player and in the admin item list. **(2) No auto-cleanup** — the health checker accumulates `consecutive_failures` on playlist items but **never disables or removes them**: `check_playlist_item` passes `is_active = None` deliberately (`src/health.rs:109` — *"Never changes `is_active` — manual intent is the source of truth"*), unlike *sources*, which auto-disable at `FAILURE_THRESHOLD = 3`. So a dead R2 item fails forever. We want on-demand items to be **automatically removed (or at least disabled) after 3 consecutive failed health checks/tune tries**, matching the source threshold. **Design points to settle:** (a) *disable* (`set_active(false)`, recoverable, reversible) vs. *hard delete* (`playlist_item::delete`, destructive — appropriate when the underlying R2 object is truly gone); (b) whether a failed *tune* try counts toward the threshold or only background health checks; (c) surfacing the removal so it isn't silent. Interacts with #48 (now done) — the shared `FAILURE_THRESHOLD` / `is_observed_down` it referenced now exists in `src/model/source.rs`; there is no `HealthAction` enum (health never mutates `is_active`). Needs a brainstorming pass.
